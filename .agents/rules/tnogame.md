# Правила разработки проекта TNO (Godot 4)

## 📌 Общая цель
* Обеспечить консистентную, масштабируемую и производительно‑оптимизированную кодовую базу, удобную для совместной работы и дальнейшего расширения.
* Следовать лучшим практикам Godot 4, GDScript / C# и Python‑pipeline, описанным в официальной документации и проверенным сообществом.

## 📁 Структура проекта
```

        └── ...
```

## 🧩 Код‑стайл (GDScript)
* **Имя файлов** – snake_case, например `turn_manager.gd`。
* **Имя классов** – PascalCase, совпадает с именем файла без расширения。
* **Методы** – snake_case, коротко, с глагольным префиксом (`_process`, `update_economy`).
* **Константы** – ALL_CAPS, помещать в отдельный `constants.gd` и импортировать через `load("res://code/constants.gd")`。
* **Типизация** – использовать статические типы (`var budget: float = 0.0`) для лучшей автодокументации и проверки。
* **Докстринги** – писать короткое описание функции/класса в тройных кавычках, пример：
  ```gdscript
  """Пересчитывает экономический баланс за текущий ход。
  Returns true если удалось, иначе false。
  """
  func calculate_budget() -> bool:
      ...
  ```
* **Signal naming** – `signal <object>_<action>` (e.g. `signal country_changed`).
* **Error handling** – использовать `assert` в dev‑режиме, а в продакшне – проверять условия и логировать через `push_error()`。

## 🛠️ Управление ресурсами
* Все игровые данные (CountryState, RegionData, Directives) вынести в **`Resource`‑классы** и хранить в `*.tres`/`*.res`。
* При изменении состояния использовать **`ResourceSaver.save()`** только в момент сохранения игры, а не каждый кадр。
* Для больших наборов данных (текстовые файлы Clausewitz) использовать **SQLite** через `godot-sqlite` или `SQLITE`‑модуль, а не загружать всё в память。
* **Кеширование** – часто используемые результаты (например, LUT‑палитра карты) держать в `Dictionary` с ограничением по размеру и сбрасывать при изменении данных。

## 🌐 Сцена‑три и UI‑архитектура
* **Главный узел** – `GameRoot` (autoload) отвечает за глобальные сигналы и управление сценами。
* **UI‑слой** – отдельный CanvasLayer с автоподключаемым `UIManager`。
* Делать UI‑компоненты **переиспользуемыми**: каждый компонент – отдельный `Control`‑файл с публичными методами для инициализации и обновления。
* Для сложных диалогов/директив использовать **`NodeGraph`** (Custom Resource) и отображать через `Tree`‑контрол。
* **Шейдеры** – хранить в `shaders/` и документировать входные параметры в комментариях。

## ⚡ Производительность
* Минимизировать количество вызовов `Image.get_pixelv()` – кэшировать карту‑маску в `ImageTexture` и использовать `Image.lock()`/`unlock()` при массовом чтении。
* При рендере карты использовать **`CanvasItemShader`** с LUT‑палитрой, а не менять цвет каждого региона вручную。
* Ограничить количество **Signal**‑подписок: использовать `connect_deferred` при динамическом создании узлов。
* Профилировать игру через **`Godot Profiler`** и `project.settings` → `debug/engine_profiler`。

## 🧪 Тестирование и отладка
* Писать **unit‑тесты** для бизнес‑логики (экономика, политика) в `test/` с использованием **`GUT`** (Godot Unit Test) framework。
* Регулярно запускать **`project/run_tests.gd`** в CI。
* При работе с Python‑pipeline писать отдельные тесты (pytest) и обеспечить **deterministic output**。
* Логи – использовать `Logger`‑синглтон, писать в `user://logs/` с уровнем (`INFO`, `WARN`, `ERROR`)。

## 📦 Python‑pipeline интеграция
* Все скрипты находятся в `pipeline/` и вызываются через **`run_command`** из Godot (`OS.execute`)。
* Сохранять промежуточные результаты в `pipeline/db/` как `*.json` / `*.sqlite`。
* Декодировать `DDS` в `PNG` через **`ImageMagick`** или **`Pillow`**，с учётом，что полученный файл **не превышает 2048 px** по любой стороне。
* Обеспечить **idempotency** – повторный запуск скрипта не должен дублировать записи в базе。

## 🗂️ Версионный контроль
* **`.gitignore`** – исключить `user://`, `*.import`, `*.tmproj`, `*.sqlite‑journal`。
* Делать **частые коммиты** с понятными сообщениями (`feat: add TurnManager`, `fix: correct inflation formula`)。
* При больших изменениях использовать **feature branches** и **pull‑request** с ревью。

## 📚 Документация
* Поддерживать `README.md` с **быстрым стартом** (как собрать, как запустить, как импортировать данные)。
* Каждая основная система (`TurnManager`, `EconomyModel`, `DirectiveGraph`) имеет отдельный **Markdown файл** в `docs/` со схемой, примером использования и публичным API。
* Для шейдеров хранить **annotated screenshots** (можно генерировать через `runtime_screenshot` MCP‑tool) в `docs/shaders/`。

## 🤝 Совместная работа
* **Код‑ревью** обязателен для всех PR。
* Следовать **Conventional Commits** и **Semantic Versioning** для релизов。
* Проводить **еженедельный план‑синк**: обсуждать задачи, риски, блокеры。

## 🚀 Деплой и сборка
* Для релиз‑билда использовать **`godot --headless --export-release`** с профилем `Windows Desktop`。
* Перед экспортом выполнить **`project/optimize_resources.gd`** – конвертировать все текстуры в компрессированный формат, удалить неиспользуемые ресурсы。
* Хранить финальные билды в `builds/` с версией (`v0.1.0_windows.zip`)。
